## Public storage API

`PlatformStore` is directly importable from `src/platform/index.ts` for host
composition. Its methods are:

```ts
createConversation(scope, input): PlatformConversation
getConversation(scope, conversationId): PlatformConversation
listConversations(scope): readonly PlatformConversation[]
acceptRun(scope, input): { run: PlatformRun; replayed: boolean }
getRun(scope, runId): PlatformRun
listRuns(scope, { statuses? }): readonly PlatformRun[]
claimRun(scope, input): { run: PlatformRun; lease: PlatformLease }
renewLease(scope, input): PlatformLease
recordDispatch(scope, input): PlatformRun
commitAnswer(scope, input): PlatformRun
failRun(scope, input): PlatformRun
requestCancel(scope, input): PlatformRun
confirmCancellation(scope, input): PlatformRun
recordMemoryOutcome(scope, input): PlatformRun
recoverExpiredLeases(scope): readonly PlatformRun[]
readEvents(scope, { after?, limit? }): PlatformEventPage
close(): void
```

Every API takes a trusted `PlatformScope` (`tenantId`, `projectId`,
`principalId`). Conversation creation generates canonical A008 runtime
conversation IDs through `RuntimeIdentityFactory`; passed conversation IDs are
validated with the existing runtime parser. `PlatformStoreError.code` uses the
frozen vocabulary including `REVISION_CONFLICT`, `CONVERSATION_BUSY`,
`COMMAND_CONFLICT`, `LEASE_LOST`, `NEEDS_RECONCILIATION`, `CAPACITY_EXCEEDED`,
`NOT_FOUND` and `INVALID_REQUEST`.

## Verified outcomes

Temporary real SQLite files prove tenant/project isolation, atomic failed
admission, receipt replay before revision/busy checks, changed-payload conflict,
single writer, stale-lease fencing, pre-dispatch requeue versus dispatched
`needs_reconciliation`, terminal cancel/completion race, atomic answer/message/
outbox behavior, separate memory failure, bounded event page/reopen, future
schema rejection and close rejection.
