## What landed

GUI upload module for ADR 0020 D3 / ADR 0019 D6, D7.

- `uploadSource(file, options?)` POSTs one file's raw bytes to
  `/v1/upload` with `content-type: application/octet-stream` and
  `x-a008-filename: <percent-encoded name>`. The filename is
  percent-encoded (`encodeURIComponent`) because a raw `Headers` value must
  be a legal ByteString and would throw a `TypeError` on accented, CJK, or
  emoji filenames otherwise; `src/ingest/types.ts` documents the stored
  filename as "advisory only," so this is a safe, low-risk choice — flagged
  as a risk to confirm against A008-0044 below.
- A 2xx body is parsed strictly into
  `{ locator, sha256, bytes, mediaType, extracted, artifactId? }`; any
  malformed field throws a named `UploadError` rather than displaying
  wrong data.
- A non-2xx response reads the host's JSON error body and surfaces its
  `message` verbatim — the same `failureMessage` pattern
  `gui/src/terminal/run-shell-command.ts` uses for `/v1/shell` — so an
  unsupported media type or an oversized file shows the server's named
  reason, never a generic "upload failed." Falls back to the HTTP status
  line only when the body is missing or non-JSON.
- A network failure (`fetch` rejects) is mapped to `UploadError` with the
  original error as `cause`; there is no retry loop and no indefinite wait,
  so an oversized or unreachable case fails visibly instead of appearing to
  hang.
- `UploadPane` is a single `<input type="file">`. Selecting a file drives
  `idle -> uploading -> done` (locator, media type, formatted size, and
  "Extracted" / "Not extracted — stored, no readable content recorded") or
  `idle -> uploading -> error` (the server's message, `role="alert"`). No
  drag-and-drop, no progress bar, no multi-file queue. The browser reads
  the file exactly once via `File.arrayBuffer()` to send its bytes; no
  parsing, no preview of document content, no provider call.
- Request uses `credentials: "omit"` and sends exactly three headers
  (`accept`, `content-type`, `x-a008-filename`) — verified by an explicit
  test asserting the full header key set, not just presence/absence of one
  name. No `Authorization` header, no `NVIDIA_API_KEY` anywhere in
  `gui/src/upload/` (grep-verified below).
- `App` mounts `<UploadPane />` between `<Composer />` and `<TerminalPane />`
  in `gui/src/app.tsx`; that file gained exactly one import line and one
  JSX element, matching ADR 0019 D7 and this charter's write scope.

## Risk the operator should know before merging

The `x-a008-filename` header value is percent-encoded
(`encodeURIComponent(file.name)`) on the client. ADR 0020 D3 states the
header only as `x-a008-filename: <original name>` with no stated encoding,
and A008-0044 (the sibling host-route task) was built in parallel with no
shared contract on this specific point. Two possible outcomes once both
land:

- If A008-0044's route `decodeURIComponent`s the header (or the ASCII
  subset round-trips unchanged, which is the common case for plain
  filenames), everything works exactly as the ADR describes.
- If it does not decode, a filename with only ASCII/Latin-1-safe
  characters is unaffected (`encodeURIComponent` leaves those bytes as-is
  for typical filenames — letters, digits, `.`, `-`, `_`), but a filename
  with spaces, accents, CJK characters, or emoji would arrive at the host
  still percent-encoded. `src/ingest/types.ts` documents the stored
  filename as "Sanitised original filename, advisory only," and it never
  participates in media-type detection (`src/ingest/media-type.ts` sniffs
  bytes only), so the worst case is a cosmetically percent-encoded display
  name — not a correctness or security issue.

Recommend the operator have A008-0044 (or an integration pass) confirm
which side is expected to encode/decode, and align if needed. This does
not block reviewing or merging this PR on its own.
