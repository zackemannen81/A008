## Delivered

`EngineHost.newSession` now accepts an internal `conversationSeed` option:

```ts
{
  conversationId: string;
  messages: readonly ChatMessage[];
}
```

It passes only through `A008AcpAgent` creation options and
`createAcpRuntime` to `LocalMemoryRuntime.openSession`; server ACP and
WebSocket request payloads do not expose this field. The runtime validates the
conversation ID with `parseRuntimeId(..., "conversation")`, accepts only
committed user/assistant history whose content passes `chatContentSchema`, and
copies each accepted message before it reaches `ChatSession`.

The seed and `workspaceConversation` are mutually exclusive before session
state/store activity. Seeded sessions do not restore, select, overwrite, or
persist legacy workspace conversations. Opening a seed performs no provider,
semantic-memory, extraction, reinforcement, or legacy-store work. The next
real user turn alone follows the current cognition/provider and post-output
pipeline, with its existing bounded history projection.

`docs/platform/CONVERSATION_SEED.md` records this internal boundary.

For the planned text-only runtime adapter: after `LocalMemorySession.turn()`
has received and committed a provider answer, a later post-output coordinator
failure rethrows from `turn()` but the committed assistant content remains
available through `session.messages`. This follows the existing owner order:
`ChatSession.send()` commits before `PostOutputMemoryCoordinator.process()`.
It is not a recovery guarantee for a provider/chat-send failure, and the
current error does not distinguish the failure phase; this task adds no API or
memory semantics for that case.
