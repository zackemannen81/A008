## Observed failure and repair

The latest owner trace returned a valid four-array empty object despite a
substantial project report and empty baseline. It was not a parse rejection.
The uncommitted prompt also contradicted strict JSON with an instruction to
explain empty results. The preceding trace returned empty arrays without that
explanation clause, so that clause alone cannot explain the omission.

The eligibility section copied from source-only extraction strongly emphasized
exclusion. This repair positively distinguishes facts established in a completed
report from narration about running commands. Eligibility is per assertion;
facts in the final answer need not also appear in the user's question.
Reinforcement remains an independent decision. Empty output always uses the
same four-array object, with no prose or additional keys.

Useful owner atomicity rules are retained and condensed: independently mutable
properties and explicit relationships get separate existing binding shapes.
Generic predicates must not summarize a resolvable technology stack or task
metadata bundle. Qualifiers, conditions and attribution stay with each fact.
The owner's 1–4 domains / 1–16 tags remain selection bounds, without padding;
classification follows each item's subject rather than only the overall report.

A live qualification probe exposed another concrete contract omission: all
three proposals were rejected for invalid `confidence` values. The prompt named
the field without its value format. It now explicitly requires numeric [0,1]
when supplied and omission of unused optional fields. Runtime validation and
state ownership are unchanged.

The original uncommitted prompt is backed up at
`%TEMP%/a008-0175-owner-prompt.ts`. Checkpoint history is preserved. No broad
rollback was performed. The source-only analyzer was left unchanged.
